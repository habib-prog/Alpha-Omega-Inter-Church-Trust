5) Security That Already Exists
============================================================
Authentication & Access:
- Email/password signup + Google login
- Email verification required before normal login access
- Protected routes block unauthenticated users
- Client checks super admin status from super_admins list

Realtime DB Rules (database.rules.json):
- public_comments:
  - read: true
  - write: auth != null
  - validation requires text/name/role/image/uid/createdAt
- users/{uid}:
  - read/write only own uid
- site_content:
  - read true, write auth != null
- super_admins:
  - read/write auth != null
- super_admin_messages:
  - read/write auth != null
  - required field validation
- admin_activity_logs and user_login_logs:
  - read/write auth != null

Additional safeguards in app:
- Admin content payload size guard (~900KB) before save
- Image upload guard in admin panel (<4MB) + in-browser compression
- Comment delete permission in UI (own comment or super admin)
- Delete account blocked for super admin accounts
- Firebase recent-login requirement handled for account delete
- Logs retention cleanup logic: old logs (>30 days) cleaned when log operations run


============================================================
6) Security Gaps / Risk Notes (Important for Review Team)
============================================================
1. High risk: write scope too broad for authenticated users
- Current rules allow ANY logged-in user to write:
  - site_content
  - super_admins
  - admin_activity_logs
  - user_login_logs
  - super_admin_messages
- This means privilege escalation and content tampering is possible unless rules are tightened.

2. Super admin check is mostly client-side logic
- UI hides admin features, but DB rules currently do not strictly enforce super-admin-only writes.

3. Sensitive operational logs readable by any authenticated user
- user_login_logs includes IP/device/location info.

4. public_comments can accept client-provided role/name/image
- User can spoof display role text (eg. pretend admin) unless server-side/rules validation is tighter.

5. Firebase config is public in client bundle (normal for Firebase)
- Must rely on strict rules + authorized domains + App Check for real protection.

10) Codebase Structure (Review Team Friendly)
============================================================
Top-level:
- src/
  - Database/firebase.config.js          -> Firebase init
  - Zustand/authStore.js                -> auth logic + role logic + logs
  - data/useSiteContent.js              -> dynamic content loader (RTDB + fallback)
  - Pages/                              -> route-level pages
  - Components/                         -> reusable UI/auth/layout/charts/inbox
- public/
  - content/*.json                      -> static fallback content
  - uploads/                            -> CMS media assets
  - admin/config.yml                    -> Decap CMS schema/config
- content/
  - newsletters/*.md                    -> newsletter source files
  - settings/organization.yml           -> org metadata
  - campaigns/*.yml/json                -> campaign content sources
- database.rules.json                   -> Realtime DB security rules
- docs/decap-cms.md                     -> CMS local workflow notes

Flow summary:
- User actions -> Firebase Auth + RTDB/Storage
- Page content -> RTDB site_content first, fallback JSON second
- Admin updates -> RTDB (custom panel) and/or file-based CMS


============================================================
11) Quick Recommendation Before External Review
============================================================
Must do first:
1) Tighten RTDB rules so only super admins can write super_admins/site_content/logs/messages-admin scope
2) Restrict read access for user_login_logs/admin_activity_logs
3) Add stronger validation on message/comment fields (length/type constraints)
4) Consider Firebase App Check + authorized domains hardening

This note reflects current implementation behavior from code scan.
